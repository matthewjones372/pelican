# 0079: Java 21

## Problem

1.0.0's library modules are compiled for Java 25, so a service on JDK 21, the
LTS most teams run, cannot use Pelican at all. Nothing in the source needs a
Java 22 to 25 API. The floor is there for one runtime behaviour: Pelican runs
synchronous handlers on a virtual thread by default, and before JDK 24
(JEP 491) a virtual thread blocked inside `synchronized` pins its carrier.
There are about as many carriers as cores, so a few handlers blocking under a
monitor (an older JDBC driver, a cache, `pelican-oidc`'s key fetch) stall
every virtual thread in the process.

## Not doing

- **Java 17.** Virtual threads are final in 21; below it the default has no
  safe form.
- **Changing the default on 24 and above.** Virtual threads, as today.
- **Falling back to the dispatcher on 21.** On the dispatcher *any* blocking
  call holds an event thread, which is the problem spec 0058 fixed.
- **Rebuilding lark.** `lark-stream` 0.9.0 is class file 69 (Java 25); that is
  lark's change to make, not this repository's.

## Shape

The default `handlers` picks by the running JDK. An explicit choice always wins.

```kotlin
api.start(port = 8080)                                    // 24+: a virtual thread per request
                                                          // 21 to 23: a bounded platform-thread pool
api.start(port = 8080, handlers = Handlers.onVirtualThreads)  // virtual on any JDK, pinning and all
```

- `Handlers` in `pelican-pekko` and `pelican-jetty` each gain an internal
  default: `onVirtualThreads` when `Runtime.version().feature() >= 24`, else
  a shared pool of 200 daemon platform threads named `pelican-handler-N`.
  Every place that defaults to `Handlers.onVirtualThreads` points at it:
  about twenty, across `start`, `toRoute`, `toHandler`, the `-docs` and
  `-mcp` mountings and `pelican-test-jetty`'s `inMemory`.
- On Jetty the pool is not `virtual`, so `start` keeps Jetty's platform
  threads on 21, which the existing flag already does.
- Library modules compile for 21. `pelican-streams` and `pelican-streams-jetty`
  stay on 25 until lark targets 21.
- `pelican-oidc` takes its key-refresh lock with a `ReentrantLock`, so a
  service that opts into virtual threads on 21 does not pin on a network fetch.

## Why this shape

A pool of platform threads keeps the one promise handler code relies on (it
may block) on every JDK, without the code knowing which it runs on. The cost
on 21 is an OS thread per request in flight, bounded. A JDK switch does mean
one service behaves differently on 21 and 25, but only in which kind of
thread runs the handler, never in what it may do. The alternative, virtual
threads everywhere plus a documented pinning caveat, is simpler and leaves a
stall that shows up under load in production. Recommended: the switch.

## Stack

- [ ] **`spec-0079-default`**: the JDK-dependent default in both backends,
      pointed at by every `handlers` default; the OIDC lock.
      Done when: a test asserts the default is the platform pool below 24 and
      virtual at 24 and above, and the parity suites pass on 25.
- [ ] **`spec-0079-target`**: `jvmToolchain(21)`, the streams modules kept on
      25, tests run on the build's JDK with a floor of 21, and a JDK 21 job in
      `build.yml` beside 25.
      Done when: `./gradlew build` passes on 21 and 25, and every published
      class but the streams modules' is major version 65.
- [ ] **`spec-0079-docs`**: README, modules, reference ("Where a handler
      runs", Versions) and choosing say Java 21, the switch and the streams
      exception; CHANGELOG under Unreleased.
      Done when: no doc says Pelican needs Java 25 except for the streams modules.

## Acceptance

```bash
./gradlew build                     # on JDK 21
./gradlew build                     # on JDK 25
javap -v -cp backends/jetty/pelican-jetty/build/classes/kotlin/main \
  io.github.matthewjones372.pelican.jetty.Handlers | grep major   # 65
```

## Open questions

1. **Pool size on 21.** Bounded at 200 (Jetty's default pool) and queueing
   past it, or unbounded (never queues, can create thousands of threads under
   a slow burst)? Recommended: 200, with `Handlers.on(executor)` for anything else.
2. **Public or internal default?** A public `Handlers.default` lets a service
   name it; internal adds no API. Recommended: internal.
3. **The streams modules.** Stay on 25 (this spec), or block on a lark release
   for 21 so everything moves together? Recommended: stay on 25.
4. **The full suite on 21, or a smoke job?** Recommended: the full suite;
   the switch is the thing that differs.
5. **Version.** Lowering the floor and adding the Jetty modules suits a minor,
   1.1.0, rather than 1.0.1, which is the snapshot's current number.
   Recommended: 1.1.0.
