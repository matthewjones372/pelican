# 0070: A response at a failure status is declared as a failure

## Problem

`pelican-health` declares its ready probe's 503 as a *success*:

```kotlin
val passing = media<HealthReport>(HEALTH_JSON, status = 200)
val unavailable = media<HealthReport>(HEALTH_JSON, status = 503)
passing or unavailable
```

The server answers it as declared, but every client reads success as 2xx,
whatever the endpoint declares:

- `ApiClient.outcome` checks `res.isSuccess` (200 to 299) before it looks at
  the declared successes, so the 503 throws `ApiCallFailed` instead of coming
  back as a value. `call` throws on anything outside 2xx.
- A generated client checks `status in 200..299` (`client-body.kt`,
  `succeeded()`), and so does every client generated by someone else.
- The document describes the 503 as "Success.".

The petshop found this moving to `pelican-health`. Its contract test cannot
read a failing report as a value; it catches `ApiCallFailed` and greps the
body for `"status":"fail"`.

Nothing at declaration stops a success at a failure status. Besides
`pelican-health`, one test does it on purpose (`ContentNegotiationTest`'s
`json<Widget>(status = 419)`, which is about the server answering an
unregistered status).

## Not doing

- Teaching clients that a 4xx or 5xx can be a success. HTTP, every generated
  client, and every gateway between them say it is not.
- Redirects. A 3xx success stays allowed; no client here follows one, and
  that is a spec of its own if it is needed.
- Changing what the probes answer or when. Only how the 503 is declared.

## Shape

```kotlin
// pelican-health
val passing = media<HealthReport>(HEALTH_JSON, status = 200)
val unavailable = errorMedia<HealthReport>(HEALTH_JSON, status = 503, "A check failed; take this out of rotation")

passing orFail unavailable
```

- **`pelican-health`'s 503 is a declared failure** carrying the same
  `HealthReport`. The probe's endpoint becomes `Outcome<HealthReport,
  HealthReport>`:
  - `client.outcome(health.ready, Unit)` is `Err(report)` when a check fails,
    and `Ok(report)` when none does;
  - `client.call(...)` still throws on the 503, as `call` does for every
    failure.
- **The document says what it is.** The 503's description is the failure's
  own ("A check failed; take this out of rotation"), not "Success.", in
  `application/health+json`.
- **A success at a failure status is refused** where it is declared, like a
  status that cannot carry a body:

  > `json<Widget>(status = 419)` declares a success at 419, and a client reads
  > anything at 400 or above as a failure. Declare it as one:
  > `json<Widget>() orFail errorJson<Widget>(419, "...")`.

- **A media-typed failure.** `errorMedia<T>(mediaType, status, description)`
  is `errorJson` for a body in another media type. `pelican-health` needs it
  for `application/health+json`, and it encodes through the codecs as JSON,
  as spec 0068's first entry made any `+json` type do.

## Why this shape

Two ways to close the gap: teach every client that a declared success may sit
at any status, or stop declaring successes at failure statuses. The first
fixes Pelican's two clients and no one else's: a client generated by
openapi-generator, a gateway, or a load balancer's health check reads a 503 as
a failure whatever the document says. The second matches what every one of
them already does, and turns the next mistake into a startup error naming the
fix. Recommended: the second.

## Stack

In this order: refusing a success at 503 before `pelican-health` stops
declaring one would stop it starting.

- [x] **`spec-0070-error-media`** ([#237](https://github.com/matthewjones372/pelican/pull/237)): `errorMedia<T>(mediaType, status,
      description)`, and a failure carrying its media type through
      `ErrorOutput` and `ErrorSpec` (with the binary-compatible constructor
      kept), the Pekko, in-memory and MCP servers, the server's codec lookup,
      the OpenAPI writer and `ApiClient`. A tagged failure is limited to a
      `+json` media type, since its tag is written into a JSON body. The
      generated client decodes failures with the JSON codec from the endpoint
      values, so a `+json` failure needs nothing there.
      Done when: an `errorMedia<T>("application/health+json", 503, …)`
      failure is answered with that content type, documented under it, and
      comes back from `outcome` as `Err`.
- [x] **`spec-0070-health`** ([#238](https://github.com/matthewjones372/pelican/pull/238)): `pelican-health` declares its 503 with
      `errorMedia`; its golden, docs and example move with it.
      Done when: `outcome(health.ready, Unit)` is `Err(report)` with the
      failing check in it, and the 503's description in the document is the
      failure's.
- [x] **`spec-0070-refuse`** ([#239](https://github.com/matthewjones372/pelican/pull/239)): a success declared at 400 or above is refused,
      one check called from the eight success outputs;
      `ContentNegotiationTest`'s 419 becomes a declared failure.
      Done when: `json<Widget>(status = 419)` is refused with the message
      above.

## Acceptance

```bash
./gradlew :pelican-core:test :pelican-test:test :pelican-health:test :pelican-openapi:test :example:test
```

Then the petshop's contract test reads the failing report as
`shouldBeError()`, and its `ApiCallFailed` workaround goes.

## Open questions

- **400 or 500 as the line?** A 4xx success is as wrong to a client as a 5xx.
  Recommended: refuse 400 and above.
- **`errorMedia`, or a `mediaType` argument on `errorJson`?** `errorJson`
  names its media type, and a failure in CSV or text is a different thing to
  ask for. Recommended: `errorMedia`, mirroring `media` beside `json` for
  successes.
- **Breaking.** A service declaring a success at 400 or above stops starting.
  Pelican is before 1.0.0 and the only declarations found are the two above.
  Recommended: refuse, and name it in the changelog.
